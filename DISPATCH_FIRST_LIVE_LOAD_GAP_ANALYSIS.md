# DISPATCH_FIRST_LIVE_LOAD_GAP_ANALYSIS

**Evidence standard:** every claim below is backed by a file, function, route, template, or test I read or ran directly against `jax1313-outlook/Dispatch` `main` at commit `48b953f` (includes the merged HOLD/Sandbox scoping change) during this session. No claim is drawn from doctrine documents, the promotion plan, comments describing intent, or memory of the earlier architectural review — where this document repeats something the earlier review found, it was re-verified fresh against current code first. Where I could not verify something directly, it is marked **UNVERIFIED**, not assumed either way.

---

## Executive Summary

- **First Live Load Ready? — YES**, via a path materially simpler than the doctrine's specified 15-step workflow, and **PARTIAL** on the doctrine's own terms if the doctrine's exact steps (Sandbox evaluation, Trip Card, Completion Packet, Email Helper, accounting handoff) are read as literal requirements rather than a target vocabulary.
- **Overall Operational Readiness — PARTIAL.** The freight execution core (intake → milestones → evidence → POD → archive → billing/settlement) is real, wired end-to-end through a working UI, and covered by a 2,414-test suite that passes clean (verified this session, exit 0). What's missing is entirely at the two ends of the process doctrine describes — a gated, checklist-shaped close, and everything after archive (customer-facing completion message, accounting handoff, non-mocked external transport).

**The single most important finding:** the doctrine's assumed workflow (Load → Evaluate → Sandbox → Mike commits → Active Load) is **not the path a manually-entered load takes today.** `POST /loads` (`portal/routes/dispatch_api.py:94`, backing `services.create_load()`) creates a load directly — no `sandbox_id`, no evaluation step, no commit gate. Sandbox/scoring/booking is a **separate, real, tested path** (`portal/models/sandbox.py`, `dispatch/scoring.py`, `tests/test_booking.py`, `tests/test_booking_pipeline.py`) used specifically for load-board-sourced opportunities (DAT/Truckstop cards), not for loads Mike enters by hand. `DEPLOY_LOCAL.md`'s own documented walkthrough (lines 107-112) uses the direct path, not Sandbox. **This means a first live load does not require Sandbox, scoring, or a "commit" step at all** — it requires four things, all of which exist: create the load, record milestones/evidence, generate POD, archive.

## Specific gaps, in the order they'd actually block or weaken a first live load

1. **No completeness gate on Close/Archive.** `archive_load()` accepts a load with no evidence and no POD. This is the highest-priority real gap: today, nothing stops Mike from archiving a load that was never actually delivered-and-documented — not a UI inconvenience, a code-level absence of any precondition.
2. **No customer-facing completion communication.** The only email `archive_load()` triggers goes to the internal reviewer, not the broker. A broker who wants confirmation, an invoice, and proof of delivery gets nothing automatically.
3. **No accounting handoff, honestly labeled as not built.** Not a blocker for "one load moves through the system," but a real gap before any load's revenue is usable data outside Dispatch.
4. **No literal Trip Card, Completion Packet, Email Helper, or their checklist/gating semantics** — the underlying data (milestones, evidence, POD, financial summary) exists and is reachable through a working UI; the doctrine's specific vocabulary and completeness-enforcing behavior do not.
5. **Scoring exists but has no caller.** Not a blocker (the manual-load path doesn't need it), but worth flagging as dead-from-the-UI code if anyone assumes evaluation happens automatically.

## What is not a gap, contrary to what the doctrine's own workflow numbering might suggest

Evaluation, Sandbox, and "commit" (doctrine steps 2-4) are not missing pieces blocking a first live load — they're a different, real, tested subsystem for a different intake source (load boards) that a manually-entered load never needs to pass through. Treating them as a blocking prerequisite would be describing a gap that doesn't exist for this path.

---

## Answer to the objective question

**Can Mike successfully complete a First Live Load using the system that exists today?**

Yes, for the core physical/operational loop: create a load, record what happens to it, attach evidence, generate a POD, and archive it — every one of those steps is real, UI-reachable, and tested. **What he would not get automatically** is a system that stops him from archiving an incomplete load, a message or document package sent to the broker on completion, or any accounting record of the transaction outside Dispatch itself. Those are real, specific, code-confirmed absences — not estimates, not doctrine gaps, not TODOs.
